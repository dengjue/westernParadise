## 1. 三条路线对比（决策留痕）

| | A · 直接改参考单文件 | B · 按规格重新生成 | **C · 标准工程化（已选）** |
|---|---|---|---|
| 做法 | 在 2.87 MB 混淆 HTML 里改文案/参数/关卡 | 参考架构与注释，重写可读 `src/NN-*.js`，构建时内联 | Vite + TypeScript + npm `three` + `vite-plugin-singlefile` |
| 代码可读性 | 极差（标识符混淆、无 source map、单行 23.8 万字符） | 好（自己写的，中文注释） | 最好（类型、模块、HMR、单元测试） |
| 起步速度 | 最快 | 快 | 较慢（要搭工程与环境） |
| 长期可维护 | **不可维护**，越改越屎山 | 可维护 | 最可维护 |
| 换主题难度 | 高 | 中 | 低 |
| 质量门禁 | 无法做 | 可加脚本 | 完整（lint / 类型检查 / 测试 / CI / 架构门禁） |
| 单文件交付 | 天然是 | 构建脚本内联即可 | 插件一键内联 |
| 适合场景 | 只想 5 分钟看个效果 | 探索期原型 + 后续迭代 | **确定要长期做 / 多人协作 / 上线** |

### 为什么最终选 C

用户 2026-11-12 明确按「长期维护、中型项目」推进。在这个定位下：

1. B 的正确内核（**源码与产物分离**）被完整保留，C 只是把它换成标准工具链实现；
2. 类型安全、依赖方向自动检查、可回归测试、可重复构建，是长期迭代的必要投入；
3. 未来若验证方向成立，无需推倒重来 —— B 的平滑迁移目标本来就是 C，现在直接到位；
4. 双产物构建让「开发体验」与「单文件离线分发」不再二选一。

代价是起步多一层工具配置、引入 Node 依赖与 `package-lock.json`；对中型项目值得。

> 原建议 B 的理由（起步轻、AI 可批量生成骨架、平滑迁 C）在**一次性探索原型**下仍成立，
> 但本项目定位已改变，故不再作为推荐结论。保留于此避免后续误读。

### 为什么不做 A

参考件标识符已压成 `gf` / `oi` / `en` / `M2`，中文文案与关卡坐标散落在 5.7 万行里，
且 `14-enemies` / 武器 / 波次等战斗逻辑与寺庙题材红线冲突 —— 要删的东西比能留的多。
在混淆代码里做减法和主题替换，是典型的屎山施工。

## 2. 单文件 vs 工程化：不冲突，分层解决

参考件「零远程资源」的成因有两层，别混淆：

| 成因 | 说明 | 对本项目是否必须 |
|---|---|---|
| **设计选择** | 素材全程序化生成（几何/贴图/音效都是代码算的），本来就没有素材文件 | ✅ 应保持，这是离线能力的基础 |
| **平台约束** | Claude Artifacts 的严格 CSP 禁止 fetch/XHR/外链，页面上限 16 MiB，逼出全内联 | ❌ 不是普遍真理 |

**结论**：

- 若目标是「**微信发一个文件、断网双击就能玩**」→ 单文件内联是刚需，必须保留；
- 若自己有服务器 / 后续做网站版 → 可以用正常多文件部署；
- **本项目两者都要**：`src/` 保持可读多文件，构建产出 `dist/site/` 与 `dist/single/index.html` 两种形态。

### 构建方式（C 定稿）

由 `vite.config.ts` 按 mode 切换，不再自写拼接脚本：

| 命令 | 产物 | 说明 |
|---|---|---|
| `npm run build` | `dist/site/` | 常规 Vite 产物，多文件、可部署 |
| `npm run build:single` | `dist/single/index.html` | `cssCodeSplit: false` + `assetsInlineLimit` 调大 + `inlineDynamicImports` + `viteSingleFile()` |

`npm run verify:single` 断言产物无 `<link>` / `<script src>` / `@import` / `url(http` / 远程端点，
并输出体积与 MD5。
`../03-工具/scan_single_html.py` 继续作为**参考件分析工具**保留，改传 `--input` 即可复跑，
两条链路互不替代：一个分析别人的单文件，一个校验自己产出的单文件。

## 3. 技术栈（C 定稿）

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **TypeScript strict**（`noUncheckedIndexedAccess` 等额外严格项） | 中型项目长期维护的第一道防线 |
| 3D 引擎 | npm `three` + `@types/three`，**按需 import** | 参考件同款；按需引入控制单文件体积 |
| 构建 | **Vite** + `vite-plugin-singlefile` | 双产物、HMR、source map、成熟生态 |
| 包管理 | npm + `package-lock.json` 入库 | 版本可复现，CI 零额外配置 |
| 质量 | ESLint(typescript-eslint) + Prettier + Vitest | 统一风格、可回归 |
| 架构门禁 | 自研 `scripts/check-layers.mjs`（零第三方依赖） | 强制单向依赖、禁循环、隔离浏览器 API |
| 材质 | `CanvasTexture` / `DataTexture` 程序化 | 无贴图文件，天然离线 |
| 音效 | Web Audio `AudioContext` + `createBuffer` | 无音频文件 |
| 字体 | 系统字体栈（PingFang SC / 系统衬线） | 无 `@font-face`，不下载 |
| UI | 原生 DOM + CSS 变量（不引入 React） | 3D 应用的 HUD 用 DOM 更直接、体积更小 |
| 输入 | 键鼠 + Pointer Lock + 触屏 + 可选 gamepad | 抽象 `InputSource` 接口，各实现并列 |
| 兜底 | 画质 4 档、UA 降级、`prefers-reduced-motion`、无 WebGL 提示、致命错误上屏 | 参考件现成的工程模式 |

### 体积预估

| 组成 | 参考件 | 本项目预估 |
|---|---:|---:|
| Three.js | ~2 MB（整库内联） | 按需引入后显著更小 |
| 业务逻辑 | ~0.7 MB | 去掉战斗/手部 SDF 后应更小 |
| CSS | 31 KB | 20–40 KB |
| **合计** | **2.87 MB** | **目标 ≤ 1.5 MB**（上限不超参考件） |

> 若体积超标，优先裁剪 Three.js 未用模块，而不是压缩可读性。

## 4. 依赖与学习成本

| 项 | 说明 |
|---|---|
| 运行时依赖 | 仅浏览器（WebGL2 优先，WebGL1 兜底）；**产物零 npm 运行时外链、零 CDN** |
| 开发期依赖 | Node 22+ / npm 10+；Python 3.9+（仅参考件分析脚本） |
| 主要学习成本 | **3D 数学 + GLSL shader**（体积光、天气、材质补丁），不是 TS 语法 |
| 现有栈适配 | Python/React/嵌入式背景 → UI 组织经验可迁移；Vite/TS 工具链与 3D 部分需上手 |
| 可跳过的高难点 | 第一人称手部 SDF、多层寻路、自定义体积雾，均非 M1 必需 |
