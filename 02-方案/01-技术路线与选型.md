## 1. 三条路线对比

| | A · 直接改参考单文件 | **B · 按规格重新生成（推荐）** | C · 标准工程化 |
|---|---|---|---|
| 做法 | 在 2.87 MB 混淆 HTML 里改文案/参数/关卡 | 参考架构与注释，重写一套可读 `src/NN-*.js`，构建时内联 | Vite + TypeScript + npm `three` + `vite-plugin-singlefile` |
| 代码可读性 | 极差（标识符混淆、无 source map、单行 23.8 万字符） | 好（自己写的，中文注释） | 最好（类型、模块、HMR、单元测试） |
| 起步速度 | 最快（改几个字符串就能跑） | 快（AI 可批量生成骨架） | 较慢（要搭工程与环境） |
| 长期可维护 | **不可维护**，越改越屎山 | 可维护 | 最可维护 |
| 换主题难度 | 高（内容散落在混淆代码里） | 中（配置与内容分离） | 低 |
| 质量门禁 | 无法做 | 可加脚本 | 完整（lint / 类型检查 / 测试 / CI） |
| 单文件交付 | 天然是 | 构建脚本内联即可 | 插件一键内联 |
| 适合场景 | 只想 5 分钟看个效果 | **探索期原型 + 后续迭代** | 确定要长期做/多人协作/上线 |

### 为什么推荐 B

1. 参考件的价值在**架构与注释**，不在代码本身；照着规格重写，比反混淆省事得多。
2. 符合你「规范先行、不允许屎山代码、按 TODO 逐项推进」的工作方式。
3. 交付仍是单文件（微信发一个文件、断网双击可玩），不牺牲参考件最吸引人的特性。
4. 后续若验证方向成立，B 的源码可以平滑迁到 C，不推倒重来。

### 为什么不推荐 A

参考件标识符已压成 `gf` / `oi` / `en` / `M2`，中文文案与关卡坐标散落在 5.7 万行里，
且 `14-enemies` / 武器 / 波次等战斗逻辑与寺庙题材红线冲突 —— 要删的东西比能留的多。
在混淆代码里做减法和主题替换，是典型的屎山施工。

## 2. 单文件 vs 工程化：不冲突，分层解决

参考件「零远程资源」的成因有两层，别混淆：

| 成因 | 说明 | 对本项目是否必须 |
|---|---|---|
| **设计选择** | 素材全程序化生成（几何/贴图/音效都是代码算的），本来就没有素材文件 | ✅ 应保持，这是离线能力的基础 |
| **平台约束** | Claude Artifacts 的严格 CSP 禁止 fetch/XHR/外链，页面上限 16 MiB，逼出全内联 | ❌ 不是普遍真理 |

**结论**：

- 若目标是「**微信发一个文件、断网双击就能玩**」→ 单文件内联是刚需，必须保留。
- 若自己有服务器 / 后续做网站版 → 完全可以用正常多文件 + CDN，用不着强求 2.8 MB 塞一个文件。
- **最稳妥的做法是两者都要**：`src/` 保持可读多文件，构建脚本把 CSS/JS 内联进 `dist/index.html`。
  开发体验与分发体验不互相牺牲。

### 构建脚本要点（阶段 2 实现）

```
读取 src/NN-*.js（按文件名排序拼接）
  → 读取 src/ui/ui.css
  → 读取 src/index.template.html
  → 内联 CSS 到 <style>，内联 JS 到 <script>
  → 输出 dist/index.html
  → 自动校验：无 <link>/<img src>/外链 script、无 http(s) 字面量（除命名空间常量）
  → 报告体积与 MD5
```

校验直接复用 `../03-工具/scan_single_html.py`，改传 `--input dist/index.html` 即可。
**拒绝硬编码路径与版本号**，全部走配置。

## 3. 技术栈建议（路线 B）

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | 原生 ES Module JS（阶段 2）→ 可平滑升 TS | 起步轻；若后续选 C 再上类型 |
| 3D 引擎 | Three.js（npm 或本地内联版本） | 参考件同款，资料最多；程序化几何/材质能力齐全 |
| 构建 | 自写 Node/Python 内联脚本（阶段 2）→ Vite 插件（阶段 3） | 先跑通再工程化，避免一上来配一堆工具 |
| 材质 | `CanvasTexture` / `DataTexture` 程序化 | 无贴图文件，天然离线 |
| 音效 | Web Audio `AudioContext` + `createBuffer` | 无音频文件 |
| 字体 | 系统字体栈（PingFang SC / 系统衬线） | 无 `@font-face`，不下载 |
| UI | 原生 DOM + CSS 变量 | HUD 用 DOM 比 canvas 内绘制更好维护 |
| 输入 | 键鼠 + Pointer Lock + 触屏摇杆 + 可选 gamepad | 参考件已验证四路输入可行 |
| 兜底 | 画质 4 档、UA 降级、`prefers-reduced-motion`、无 WebGL 提示、致命错误上屏 | 参考件现成的工程模式 |

### 体积预估

| 组成 | 参考件 | 本项目预估 |
|---|---:|---:|
| Three.js 整库内联 | ~2 MB（大头） | 同量级；若按需引入可显著减小 |
| 游戏逻辑 | ~0.7 MB | 去掉战斗/手部 SDF 后应更小 |
| CSS | 31 KB | 20–40 KB |
| **合计** | **2.87 MB** | **1.5–2.5 MB**（目标控制在参考件以内） |

> 若体积超标，优先裁剪 Three.js 未用模块，而不是压缩可读性。

## 4. 依赖与学习成本

| 项 | 说明 |
|---|---|
| 运行时依赖 | 仅浏览器（WebGL2 优先，WebGL1 兜底）。**零 npm 运行时依赖、零 CDN** |
| 开发期依赖 | Python 3.9+（分析脚本）；Node（若用 Vite）；Three.js 源码一份 |
| 主要学习成本 | **3D 数学 + GLSL shader**（体积光、天气、材质补丁），不是 JS 语法 |
| 你的现有栈适配 | Python/React/嵌入式背景 → React 经验可迁移到 UI 组织；3D 部分需新学 |
| 可跳过的高难点 | 第一人称手部 SDF、多层寻路、自定义体积雾，均非首个里程碑必需 |
